# Running Behind a Reverse Proxy

By default the container terminates TLS itself and obtains certificates automatically for `SERVER_NAME`.
If TLS is terminated by an external reverse proxy instead (e.g. a shared Caddy, nginx or Traefik serving several
applications), two settings are required.

---

## 1. Serve Plain HTTP

Let the container listen on plain HTTP only, and do not publish its ports to the outside:

```yaml
    environment:
      - SERVER_NAME=:80
```

`:80` answers requests for any host name. To answer only for the site's own host name, use
`SERVER_NAME=http://humhub.example.com` instead; this requires the proxy to pass the original `Host` header
through, which the proxies below do.

The [health check](healthcheck.md) follows `SERVER_NAME` and probes the container over plain HTTP in both cases
(images built on or after October 23, 2026; earlier images always probe `https://localhost` and stay unhealthy
on plain HTTP).

---

## 2. Trust the Proxy

The container now only sees plain HTTP requests from the proxy. HumHub ignores the `X-Forwarded-*` headers of a
proxy it does not trust, so it generates all absolute URLs with `http://` although the site is served over HTTPS.
Browsers block these as mixed content, which breaks for example:

- live updates (the Mercure `EventSource` to `/.well-known/mercure`)
- file downloads and previews
- theme assets, such as fonts and stylesheets

Declare the IP range of your proxy as trusted:

```yaml
    environment:
      - HUMHUB_WEB_CONFIG__COMPONENTS__REQUEST__TRUSTED_HOSTS=["172.16.0.0/12"]
```

From these addresses, HumHub accepts the `X-Forwarded-Proto`, `X-Forwarded-Host`, `X-Forwarded-Port` and
`X-Forwarded-For` headers. This fixes all generated URLs at once, so there is no need to override single URLs such as
`HUMHUB_CONFIG__COMPONENTS__LIVE__DRIVER__HUB_URL`.

The `HUMHUB_WEB_CONFIG__` prefix applies the setting to web requests only. Do not use the usual `HUMHUB_CONFIG__`
prefix here: it also configures the console application, whose request component has no such property, so every
`yii` command fails, including the migrations at container start, the scheduler and the queue workers.

The value is a JSON list of addresses or CIDR ranges. `172.16.0.0/12` covers the subnets Docker allocates by
default (`172.17.0.0/16` to `172.31.0.0/16`); check the actual subnet of the network the proxy uses to reach the
container with `docker network inspect <network>`, and prefer that subnet (e.g. `["172.18.0.0/16"]`) or the fixed
address of the proxy.

> **Security:**
> Anyone who can reach the container from a trusted address can spoof these headers, e.g. fake the visitor IP
> recorded in sessions and logs, or the host name used in generated links. Only trust the address range of your
> proxy, and make sure the container is not reachable from anywhere else:
> - Don't publish the container ports at all if the proxy runs in Docker (see the example below).
> - If the proxy runs on the host, publish the port on the loopback interface only, e.g. `127.0.0.1:8080:80`.
>   Connections via the loopback address (and, on Docker Desktop, all connections) reach the container from the
>   Docker gateway address (e.g. `172.18.0.1`), which lies within the trusted range. Other local processes can
>   therefore spoof the headers too, but a port published on a public interface would in addition let anyone reach
>   HumHub without the proxy.

Trusting `X-Forwarded-For` also makes HumHub record the real visitor IP addresses (e.g. in sessions and logs) instead
of the proxy's. For the Caddy access log of the container, see [Logging](logging.md#client-ip-behind-a-reverse-proxy);
that setting is independent of this one and does not change what HumHub sees.

### Existing installations

HumHub stores the **Base URL** (Administration > Settings > General) during installation from the first request,
and uses it for links in e-mails and notifications generated by the background workers. If the instance was
installed or run behind the proxy before it was trusted, that setting may still start with `http://`; correct it
once.

## Example

HumHub joins the network of the proxy; no ports are published:

```yaml
services:
  humhub:
    image: humhub/humhub:stable
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    volumes:
      - ./humhub-data:/data
    networks:
      - default
      - proxy
    environment:
      - SERVER_NAME=:80
      - HUMHUB_WEB_CONFIG__COMPONENTS__REQUEST__TRUSTED_HOSTS=["172.16.0.0/12"]
      - HUMHUB_CONFIG__COMPONENTS__DB__DSN=mysql:host=db;dbname=humhub
      - HUMHUB_CONFIG__COMPONENTS__DB__USERNAME=root
      - HUMHUB_CONFIG__COMPONENTS__DB__PASSWORD=changeMe
  db:
    # see README.md

networks:
  proxy:
    external: true
```

The proxy reaches the container as `humhub` on the `proxy` network. The database stays on the project's default
network only.

### Caddy

Caddy sets the `X-Forwarded-*` headers and streams the Mercure events without further configuration:

```caddyfile
humhub.example.com {
    reverse_proxy humhub:80
}
```

### nginx

nginx needs the headers set explicitly, and buffering disabled for the Mercure event stream.
`client_max_body_size` should match the [upload limit](php-configuration.md) of the container.
`X-Forwarded-Host` is required: without it HumHub falls back to the container's own port and generates URLs
with `:80`. Keep the `proxy_set_header` directives at `server` level: nginx does not inherit them into a
`location` that sets a `proxy_set_header` of its own.

```nginx
server {
    listen 443 ssl;
    server_name humhub.example.com;
    # ssl_certificate ...

    client_max_body_size 1G;

    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Host $http_host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    location / {
        proxy_pass http://humhub:80;
    }

    # Mercure event stream (Server-Sent Events): pass it through unbuffered and keep it open
    location /.well-known/mercure {
        proxy_pass http://humhub:80;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 24h;
    }
}
```

### Traefik

Traefik sets the `X-Forwarded-*` headers by default and streams the Mercure events. Route the HTTPS entry point
to port `80` of the container, e.g. with labels on the `humhub` service:

```yaml
    labels:
      - traefik.enable=true
      - traefik.docker.network=proxy
      - traefik.http.routers.humhub.rule=Host(`humhub.example.com`)
      - traefik.http.routers.humhub.entrypoints=websecure
      - traefik.http.routers.humhub.tls=true
      - traefik.http.services.humhub.loadbalancer.server.port=80
```

## Verifying

Open HumHub in the browser and check the developer console: there must be no `Mixed Content` warnings, and the
network tab shows the `EventSource` request to `https://humhub.example.com/.well-known/mercure`.

From the shell, the live module configuration embedded in the page must contain the `https://` hub URL:

```bash
curl -s https://humhub.example.com/user/auth/login | tr -d '\\' | grep -o 'http[s]*://[^"]*/.well-known/mercure'
```
